# агент exp-1

<img src="assets/exp-1-logo.png" alt="exp-1 logo" width="96" />

Мінімальний агент для написання коду на Rust із термінальним інтерфейсом, який розмовляє з **27 провайдерами**, видаючи кожному список моделей, які той насправді обслуговує: каталог надходить наживо з models.dev, а таблиця в бінарнику слугує офлайн-запасним варіантом. П'ять протоколів передачі покривають їх усі — API **OpenAI chat-completions**, який використовує десяток постачальників, **OpenAI Responses**, **Anthropic messages**, рідний **Gemini `generateContent`** від Vertex AI та бекенд Codex, — а провайдер входить з API-ключем, сторінкою з кодом пристрою, власним входом постачальника або обліковими даними, які вже зберігає машина. Шлях Codex з'явився першим і досі лишається одним із них: ChatGPT OAuth на `auth.openai.com`, а запити йдуть на `https://chatgpt.com/backend-api/codex/responses`.

## Що він робить

- Потоково виводить відповіді з ендпойнта Codex Responses (SSE, розбирається вручну).
- Крутить цикл агента — запит → потік → виконати інструмент → повернути вивід назад → повторити — доки модель не перестане просити інструменти.
- Тримає дві гілки: основну розмову та бічну гілку для запитань, які не повинні її переривати.
- Показує міркування, потоковий текст асистента, виклики інструментів та їхній вивід в одній стенограмі, з тривалістю кожного ходу та часом за годинником.

## Інструменти

| Інструмент | Аргументи | Примітки |
| --- | --- | --- |
| `read` | `path`, `limit?`, `pos?` | Щонайбільше 400 рядків за замовчуванням; `limit` це змінює, `pos` — перший рядок, з відліком від 1. Вивід нумерується, а обрізане читання підказує, як продовжити. Файл на 3000 рядків проходиться частинами навмисно: проковтнути його цілком — це десятки тисяч токенів. |
| `write` | `path`, `content` | Створює батьківські каталоги; перезаписує наявний файл. |
| `edit` | `path`, `old`, `new`, `edits?` | Точна заміна, усе або нічого. Невдача називає найближчі рядки або позиції збігів, тож розбіжність у пробілах не коштує повторного читання. `edits` приймає кілька пар `{old, new}` для одного файлу за один виклик. Результат показує, що змінилося. |
| `fetch` | `url`, `limit?`, `pos?` | Одна сторінка як звичайний текст, з посторінковим доступом, як до файлу: `limit` рядків (типово 400) від `pos` (з відліком від 1). Скрипти та стилі відкидаються, сутності декодуються. |
| `count` | `path`, `refresh?` | Кількість рядків у файлі або в усіх файлах під каталогом, без читання вмісту. Кешується окремо для кожного файлу в `.cache/count`, за ключем з розміру та mtime. |
| `grep` | `pattern`, `path?`, `include?`, `max?` | Пошук за регулярним виразом у файлі або дереві, не втягуючи файли в розмову. `include` фільтрує за іменем файлу (`*.rs`). Пропускає `.git`, `.cache`, `target`, `node_modules`; не переходить за символьними посиланнями; ігнорує нетекстові файли. Обмежений `max` збігами (типово 100). |
| `delete` | `path` | Видаляє файл. Каталоги відхиляються — спустошувати дерево належить у `shell`, де видно всю команду. |
| `shell` | `command`, `background?`, `limit?`, `output_id?` | Команда на передньому плані блокує агента до свого завершення; після 60 с вона переводиться у фоновий режим, і агентові повідомляють, коли вона завершиться. `background: true` одразу повертає id. Фонові команди ніколи не вбиваються за таймером. Вивід обмежено 30 000 байтами: довший зберігає початок і кінець, а пропуск позначено. `output_id` перечитує будь-який попередній запуск з іншим `limit`. |
| `ast` | `path?`, `refresh?` | Дерево проєкту у форматі `tree`. Кешується в `.cache/ast`; `refresh: true` перебудовує. `.git` пропускається. |
| `websearch` | `query`, `numResults?`, `type?`, `livecrawl?`, `contextMaxCharacters?` | Вебпошук із вмістом сторінок. Використовує хостинговий MCP від Exa на `mcp.exa.ai`, який **не потребує API-ключа**; встановіть `EXA_API_KEY`, щоб зняти обмеження швидкості. `type` — це `auto`/`fast`/`deep`. |
| `ask_question` | `question`, `options?`, `label?`, `submit?` | Блокує хід і показує панель запитань. `↑↓` вибирають варіант, `Tab` переходить між запитаннями, `Enter` підтверджує, `Esc` закриває. Усе набране вважається вільною відповіддю і переважає виділений варіант. |

Команди shell виконуються без пісочниці від імені користувача. Команда на передньому плані переводиться у фоновий режим через 60 секунд, ніщо не вбиває фонову команду за таймером, а вивід обмежено 30 000 байтами: довший результат зберігає початок і кінець, а пропуск позначено як пропущений.

Інструмент `web` шукає в інтернеті: спершу хостинговий MCP від Exa, бо він повертає вміст сторінки, а коли спільний безкоштовний тариф Exa впирається в обмеження швидкості — HTML-сторінку DuckDuckGo. `EXA_API_KEY` перемикає Exa на ваш власний тариф і є єдиним налаштуванням, потрібним обом шляхам.


## Платформи

Агент — це одна кодова база для Linux, macOS і Windows: TUI, цикл агента, провайдери, MCP, навички, сесії та вбудований titler — звичайний Rust, який працює всюди. Частини, що торкаються операційної системи, мають по одній гілці на платформу:

| | Linux | macOS | Windows |
| --- | --- | --- | --- |
| TUI, агент, провайдери, MCP, навички, сесії | так | так | так |
| Відкриття сторінки входу | `xdg-open` | `open` | `cmd /C start` |
| Перевірка живучості демона та його зупинка | `kill` 0 / SIGTERM→SIGKILL | те саме | `tasklist` / `taskkill /T`, потім `/F` |
| Сервер, відокремлений від своєї консолі | `process_group(0)` | те саме | `DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP` |
| Каталоги конфігурації та стану | `$XDG_*`, `~/.config` | `$XDG_*`, `~/.config` | `%APPDATA%`, `%LOCALAPPDATA%` |
| Зображення з буфера обміну (`ctrl + v`) | `wl-paste`, `xclip` | `pngpaste` | PowerShell + `System.Windows.Forms` |
| Сповіщення про завершення ходу | `notify-send` | `osascript` | спливна підказка PowerShell |
| Встановлення з архівів (`exp-1 install *.zip`) | `unzip` / `tar` | те саме | `tar` (bsdtar читає zip) |
| Локальні MCP-сервери з іменем `npx` | як написано | як написано | повторюються як `npx.cmd` |

Гілки демона та буфера обміну для Unix і Windows було перевірено на компіляцію, тимчасово активувавши їх на Linux; `creation_flags` — єдиний виклик, доступний лише у Windows, який неможливо перевірити без Windows-цілі, і ніщо з цього не запускалося на справжній машині з Windows чи macOS.

### Кросзбирання з Linux

Бінарник для Windows збирається на Arch із тулчейном mingw (для цього один раз потрібен root):

```sh
sudo pacman -S --needed mingw-w64-binutils mingw-w64-gcc
rustup target add x86_64-pc-windows-gnu
cargo build --release --target x86_64-pc-windows-gnu
```

`dlltool` з `mingw-w64-binutils` — саме те, що потрібно бібліотекам імпорту; без нього збирання зупиняється на `windows-sys`.

Без root той самий бінарник виходить із tarball llvm-mingw, розпакованого під `~/.local`. Rust std для цієї цілі просить у лінкера `libgcc.a`, якого llvm-mingw не постачає, тож прокладка з двох символьних посилань дає еквіваленти, а `--no-default-features` прибирає вбудований titler так само, як це робить CI:

```sh
mkdir -p ~/.local/mingw-shim
ln -sf ~/.local/llvm-mingw/lib/clang/*/lib/windows/libclang_rt.builtins-x86_64.a ~/.local/mingw-shim/libgcc.a
ln -sf ~/.local/llvm-mingw/x86_64-w64-mingw32/lib/libunwind.a ~/.local/mingw-shim/libgcc_eh.a
PATH="$HOME/.local/mingw-shim:$HOME/.local/llvm-mingw/bin:$PATH" \
CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER="$HOME/.local/llvm-mingw/bin/x86_64-w64-mingw32-clang" \
RUSTFLAGS="-L $HOME/.local/mingw-shim" \
cargo build --release --target x86_64-pc-windows-gnu --no-default-features
```

`cargo` і `rustup` з `~/.cargo/bin` знають крос-цілі; системні пакунки — ні, а на цій машині `~/.cargo/bin` відсутній у `PATH`, тож викликайте їх за повним шляхом.

Бінарник для macOS теж не потребує root, і з `cargo zigbuild` усе дерево збирається під `aarch64-apple-darwin`: `zig cc` крос-компілює C-залежності (включно з `aws-lc-sys`, чого звичайний `cargo check` не може — хостовий `cc` відкидає `-arch arm64`), і кожен крейт компілюється. Зупиняє все це останній крок: фіча `rustls` у `reqwest` 0.13 тягне `rustls-platform-verifier`, і лінкер тоді повідомляє `unable to find framework 'Security'` та `'CoreFoundation'`. Вони є лише в Apple SDK; Zig лінкує Mach-O і libSystem без проблем, але фреймворків не постачає. Тож бінарники для macOS надходять із Mac або з CI (`.github/workflows/release.yml` збирає обидві архітектури). Наведений нижче рецепт — той, що доходить до лінкування:

```sh
mkdir -p ~/.local/zig && curl -L https://ziglang.org/download/0.14.1/zig-x86_64-linux-0.14.1.tar.xz \
  | tar -xJ -C ~/.local/zig --strip-components=1
cargo install cargo-zigbuild
rustup target add aarch64-apple-darwin
PATH="$HOME/.local/zig:$PATH" cargo zigbuild --release --target aarch64-apple-darwin
```

Результат не підписано. На Apple Silicon непідписаний бінарник убивається при запуску, тож його треба один раз підписати на самому Mac:

```sh
codesign -s - --force ./exp1-agent        # ad-hoc signature
xattr -cr ./exp1-agent                    # if it arrived by download
```

## Вимоги

- Rust 1.85+ (редакція 2024)
- Або наявний вхід у Codex CLI (його `auth.json` використовується повторно), або `/login`, який сам виконує той самий потік пристрою.
- Вбудований титлер, скомпільований в агент із `src/titler.rs` під фічею `titler`. Він тягне за собою Candle, тому перше збирання триває довго, а бінарник важить ~21 МБ, а не ~14 МБ. Коли ваги в кеші Hugging Face, генерування назв працює офлайн.

## Встановлення

Для встановлення останньої версії з crates.io потрібні Rust 1.85+ і Cargo:

```sh
cargo install exp1-agent
exp1-agent --help
```

Cargo встановлює бінарник `exp1-agent` у `~/.cargo/bin`; за потреби додайте цей каталог до `PATH`. Стандартна збірка містить локальний титлер, тому перше встановлення триває довше, поки компілюється Candle.

## Використання

```sh
cargo run --release                      # uses the current directory
exp1-agent --model gpt-6-luna --effort high # pick a model and reasoning effort
exp1-agent --cwd ~/projects/my-app          # run the shell tool somewhere else
exp1-agent --help
```

| Клавіша | Дія |
| --- | --- |
| `Enter` | Надіслати промпт або виконати команду, коли її вже набрано повністю |
| `↑` `↓` | Рухати вибір у списку доповнень або викликати попередні промпти |
| `Tab` | Прийняти виділене доповнення |
| `Ctrl + /` | Перемикатися між основною та бічною гілкою |
| `Ctrl + Shift + A` | Перемикати режим дозволів: always ask → never ask → ask only commands |
| `Esc` | Сам по собі нічого не робить |
| `Esc` `Esc` | Перервати поточний хід або закрити список доповнень чи панель вибору |
| `Ctrl-C` | Вийти |
| `Ctrl-U` | Очистити рядок введення |
| `Ctrl-Backspace` | Видалити попереднє слово |
| `Ctrl-Delete` | Видалити наступне слово |
| `Ctrl-W`, `Alt-Backspace` | Те саме, що `Ctrl-Backspace` |
| Колесо миші | Прокручувати стенограму |
| `PgUp` / `PgDn` | Прокручувати стенограму |
| `←` `→` `Home` `End` | Рухати курсор |
| `Backspace` / `Delete` | Редагувати |

Стрілки ходять історією промптів: після надсилання `hi` клавіша `↑` повертає його в поле, подальші натискання йдуть далі назад, а `↓` веде вперед до порожнього поля. Прокручування — на колесі миші, тож стрілки залишаються вільними для історії.

Введення `/` відкриває список доповнень, відфільтрований за префіксом. Після пробілу він доповнює й аргументи команди — `/themes <tab>` показує схеми, `/model <tab>` — моделі, а `/model gpt-6-luna <tab>` — зусилля міркування. `Enter` на голому `/model` чи `/themes` натомість відкриває нумерований список вибору; `/model` — це два кроки: спершу модель, потім зусилля. За порожнього поля курсор стоїть на самому початку, перед підказкою-заповнювачем.

Рядок підказки змінюється залежно від контексту. Введення заблоковано, поки триває хід.

`Esc` навмисно нічого не робить; перериває подвійне натискання. Переривання скасовує поточний запит і відкидає будь-який частковий текст асистента, залишаючи історію розмови недоторканою.

Обробляються локально; вони ніколи не доходять до моделі.

| `/help` | Показати клавіатурні скорочення |

## Інтерфейс

Компонування повторює TUI від OpenAI Codex: без панелей із рамками, шапка `>_` з робочим каталогом під нею, спливне вікно доповнень або нумерована панель вибору над полем введення, смуга введення з відступами, промптом `›` і блимаючим курсором `│`, а потім рядок моделі та рядок підказки.

- Надісланий промпт малюється у стенограмі як смуга на всю ширину, так само, як це робить Codex.
- **Вивід інструментів приховано за замовчуванням**: стенограма несе виклик (`read src/main.rs`), а не те, що він повернув. `ctrl-o` показує вивід під його викликом і ховає знову — це та різниця між тим, щоб стежити за роботою, і тим, щоб читати її.
- **Миша — не лише для прокручування.** Колесо прокручує, перетягування виділяє та копіює, а клік діє на те, на що він упав: рядок панелі вибору чи спливного вікна доповнень поводиться як Enter на цьому рядку, підказка `ctrl + / for side` в нижньому рядку перемикає гілки, а посилання в повідомленні відкривається в браузері. Кожен кадр записує намальовані ним області, тож клік — це перевірка попадання по останньому кадру, а не здогад про компонування. Підсвічування при наведенні навмисно не реалізовано: воно коштує перемальовування на кожен рух миші, а власний курсор термінала вже показує, де вказівник.
- Субагент звітує про поточний крок **одним рядком, що оновлюється** (`subagent → grep tokenizer`), а не рядком на крок, і виклик, який його почав, виглядає як `task: <description>`.
- **Клік на власному повідомленні запитує, що з ним робити**, а не робить це: маленьке меню з `copy` (текст потрапляє в буфер обміну) та `revert`. Повернення відкидає все після цього повідомлення — розмову, те, що було сказано моделі нижче цієї точки, і кожну зміну файлів, яку зробили подальші ходи й повертає журнал скасувань. Саме повідомлення зникає зі стенограми, а його текст повертається в промпт, тож його можна відредагувати й надіслати знову. Текст перевіряється, перш ніж щось відкидається, тож клік, що влучив не в те повідомлення, нічого не робить.
- Стенограма тримається найновішого повідомлення; колесо миші або `PageUp`/`PageDown` прокручують угору історією, `ctrl-g` повертає до найновішого повідомлення, а `ctrl-t` — до найстарішого, і прокручений угору вид залишається на місці, поки надходять нові рядки, замість того щоб його тягло назад донизу.
- Перетягування мишею виділяє текст будь-де на екрані — включно з шапкою — а відпускання кладе його в буфер обміну: спершу OSC 52, тож це працює і через ssh, а далі `wl-copy`, `xclip` чи `xsel`, коли вони є. Примітка `copied N chars` підтверджує це в рядку підказки. Виділення — це стриманий відтінок позаду тексту, і воно спиняється на останньому символі кожного рядка, як поводиться власне виділення термінала. Термінал ніколи не бачить перетягування, бо застосунок тримає мишу для прокручування, тож це єдиний спосіб копіювати.
- Прикріплена картинка показується як заповнений чип `Image 1` над промптом, поруч із ним `ctrl-v replaces it`, тож те, що ось-ось буде надіслано, видно в самій смузі введення.
- Поки триває хід, рядок активності стоїть **безпосередньо під промптом, до якого належить** — з власною міткою для кожної дії: `⠋ thinking 4s`, поки запит у дорозі, `⠋ preparing write… (12 KB) 8s`, поки модель ще пише аргументи виклику інструмента, `⠋ running 4s`, поки інструмент виконується. Кожна мітка має власний лічильник, тож секунди стосуються того, що відбувається зараз, і ніколи не рахують увесь хід; загальний час ходу показує `Worked for` наприкінці. Нижній рядок залишається простою міткою `GPT-6-Luna high · /path · <thread> · Main [default]`; `esc esc interrupts` живе в рядку підказки.
- Після завершення ходу до стенограми дописується `Worked for 5s · 12:08 PM`.
- Рядок моделі виглядає як `GPT-6-Luna high · /path · <thread name> · Main [default]` або `… · Agent` у бічній гілці. Назва гілки береться з першого промпту.
- Рядок підказки несе перемикач гілок праворуч, червоний, поки активна бічна гілка.
- Порожній екран залишається тихим: повний список команд з'являється лише на машині, яка ще жодного разу не зберегла розмову, а після цього це один рядок, що вказує на `/` та `/help`.
- Введення залишається живим під час ходу, тож запитання `/btw` можна поставити, не чекаючи.
- `/btw` або `ctrl + /` відповідає в бічному чаті, який несе всю основну розмову як контекст, нічого до неї не додаючи.
- `shift + tab` перемикає між режимами build і plan; нижній рядок показує `plan mode`, поки його увімкнено.
- Хід, що триває довше п'ятнадцяти секунд, дзвонить у термінальний дзвіночок (і викликає `notify-send`, де він є в робочому столі), коли завершується, тож за довгою роботою не треба стежити.
- `shift + enter` вставляє розрив рядка замість надсилання, тож промпт може бути з кількох рядків; смуга введення росте, щоб їх вмістити.
- `ctrl + v` бере зображення з буфера обміну (Wayland `wl-paste`, X11 `xclip`) і прикріплює його до наступного промпту, показуючи `▣ image attached` у рядку підказки, доки його не надіслано. Картинка передається як data URL, тож бекенди Codex, OpenAI, Anthropic і Gemini її всі передають далі.
- `ask_question` викликає панель над полем введення, дзеркалячи інструмент Question: акцентна смуга вздовж лівого краю, заголовок `Questions`, вкладки, коли кілька запитань ставлять разом, нумеровані варіанти з виділеним серед них, слот `Type your own answer` і `⇥tab ↑↓ select enter confirm esc dismiss` внизу.

Кольори — truecolor, тож тема термінала не може їх переозначити. Модель, зусилля та тему можна перемикати під час роботи через `/model` і `/themes`.

Навмисні відмінності від Codex: у Codex є `/permissions` і `/review`, які потребують політики пісочниці та рецензента діффів; ця збірка натомість має `/clear` і `/help`. Нижній рядок Codex рекламує оверлеї агента та скорочень, яких у цьому MVP немає.

## Автентифікація

`/login` виводить список провайдерів, і вхід у кожен улаштовано так, як очікує його постачальник:

- **API-ключ** для більшості з них, що надсилається як `Authorization: Bearer` (або `x-api-key` для API Anthropic) і зберігається окремо для кожного провайдера в `~/.config/exp-1/credentials.json` з правами `0600`. Один ключ може покривати кілька провайдерів — `opencode-go` і `opencode-zen` — це один акаунт за двома базовими URL, а `providers::key_group` називає групи.
- **Вхід за кодом пристрою** для `openai (auth)`, `github copilot` і `meta (auth)`: у браузері відкривається сторінка входу постачальника, а URL і код друкуються як запасний варіант.
- **Токен із власного входу постачальника** для `anthropic (auth)`, що надсилається із заголовками ідентичності офіційного клієнта.
- **Облікові дані, які машина вже має**, для `google vertex`: те, що налаштував `gcloud auth application-default login`, причому `GOOGLE_CLOUD_PROJECT` і `GOOGLE_CLOUD_LOCATION` називають проєкт і регіон. Нічого не треба вставляти.

Шлях Codex також веде власний файл: під час першого запуску агент копіює `$CODEX_HOME/auth.json` (типово `~/.codex/auth.json`) у `~/.exp1-agent/auth.json` і працює з цієї копії. **Ваші справжні облікові дані Codex ніколи не перезаписуються.** Коли токену доступу лишається 5 хвилин до завершення, агент оновлює його:

```
POST https://auth.openai.com/oauth/token
grant_type=refresh_token
client_id=app_EMoamEEZ73f0CkXaXp7hrann
```

Відповідь ротує refresh-токен, тож новий записується назад у власну копію агента. Збережений файл записується атомарно з правами `0600`.

## Моделі та зусилля

Ані список моделей, ані зусилля міркування не зашиті в код. Обидва читаються з власного каталогу Codex CLI за `$CODEX_HOME/models_cache.json` (типово `~/.codex/models_cache.json`), використовуючи `slug`, `display_name`, `description`, `visibility`, `default_reasoning_level` і `supported_reasoning_levels` кожного запису. Типовою на старті є перша в цьому каталозі модель.

**Кожен інший провайдер отримує свій список наживо, з models.dev.** Каталог завантажується щонайбільше раз на дванадцять годин у `~/.cache/exp-1/models-dev.json`, тримається в пам'яті й читається задля трьох речей: ідентифікаторів моделей, які пропонує провайдер, протоколу, яким говорить кожна модель (models.dev записує його як пакет AI SDK, з яким налаштовано провайдера — `@ai-sdk/anthropic` для моделі Claude за шлюзом, `@ai-sdk/openai` для Grok), і вікна контексту, з якого обчислюється поріг автоматичного ущільнення. Провайдер, відсутній у каталозі, лишається з таблицею в `src/providers.rs`, як і машина без мережі, тож застосунок ніколи не залежить від цього завантаження.

Модель, якої немає в таблицях узагалі, все одно отримує протокол: його визначає префікс постачальника (`claude-*`, `minimax-*` і `qwen-*` говорять Anthropic, `grok-*`, `gpt-*` і `muse-*` говорять Responses, `gemini-*` говорить Gemini, усе інше — chat), а провайдер, який говорить одним протоколом завжди, відповідає й за все інше.

**Панель вибору показує кожного провайдера, у якого виконано вхід**, однією полицею, а не по одній на вхід: рядки несуть `via <provider>`, щоб розрізнити два капелюхи на одній назві моделі, провайдер, який використовується, іде першим, а вибір моделі іншого провайдера спершу перемикає на нього. Таку довгу полицю шукають набором: кожна панель фільтрує в міру набору, backspace розширює збіг, а Escape розширює, перш ніж закритися. Область у `/scoped-models` фільтрує ту саму полицю й називає модель одного провайдера (`opencode-go/grok-4.7`), тож однакова назва від двох провайдерів — це два записи; старіша область із голими назвами все ще означає «ця назва, від будь-якого провайдера», а `ctrl-a` у тій панелі очищає область, що знову пропонує все. `/model grok-4.7` бере провайдера, який використовується, коли таку назву пропонують кілька, а `/model opencode-go/grok-4.7` називає одного точно.

Зусилля справді різняться від моделі до моделі, тому вгадувати їх не виходить:

| Модель | Зусилля |
| --- | --- |
| `gpt-5.6-terra` | low, medium, high, xhigh, max, **ultra** |
| `gpt-6-luna` | low, medium, high, xhigh, max |
| `gpt-5.5` | low, medium, high, xhigh |

Панель вибору зусиль, доповнення `/model <name> <tab>` і перевірка — усі йдуть за активною моделлю. Перемикання моделей переносить зусилля, коли нова модель його приймає, а інакше відкочується до її `default_reasoning_level`, тож ви ніколи не опинитеся в стані, коли просите зусилля, якого модель не має:

```
/model gpt-5.6-terra ultra   →  GPT-5.6-Terra ultra
/model gpt-5.5               →  GPT-5.5 medium          (ultra is not a gpt-5.5 level)
/model gpt-5.5 max           →  'max' is not a GPT-5.5 level;
                                this model takes low, medium, high, xhigh
```

У панелі вибору з'являються лише моделі з `visibility: "list"`; приховані лишаються доступними за назвою. Якщо файл каталогу відсутній, застосунок відкочується до стриманого вбудованого списку, щоб лишатися придатним, і повідомляє про це в панелі вибору.

Відповідатимуть насправді лише ті моделі, на які має право підключений акаунт ChatGPT — решту бекенд відхиляє з пояснювальною помилкою.

## Відображення

Відповіді асистента відображаються як багатий текст у самому процесі. Немає зовнішнього рендерера, немає `pandoc`, немає бінарника TeX, немає растеризації зображень — усе відбувається всередині TUI, тож це майже нічого не коштує.

- **Markdown**: заголовки, жирний шрифт, курсив, вбудований код, блоки коду з боковою смугою та тегом мови, марковані та нумеровані списки, цитати, горизонтальні лінії, посилання, pipe-таблиці у стилі GitHub із рамками з псевдографіки та вирівнюванням за колонками, і вбудована математика `$…$`.
- **Математика LaTeX**: символи та відношення, грецька, `\frac`, `\sqrt`, нижні та верхні індекси, `\mathbb` і `\mathcal`, комбіновані діакритичні знаки (`\bar`, `\hat`, `\vec`, …), назви операторів прямим накресленням (`\log`, `\sin`, `\lim`, …) і виносні блоки `$$…$$`.

Усе, чого конвертер не розпізнає, виводиться дослівно, разом із фігурними дужками, тож незнайомий вхід лишається читабельним, а не перетворюється на місиво. Це конвертер, а не рушій TeX: макроси, середовища на кшталт `tikz` і багаторядкові компонування не інтерпретуються.

Markdown розбирається **один раз**, коли надходить повідомлення, на фрагменти, незалежні від теми; малювання лише зіставляє ці фрагменти з кольорами. Тому перемикання тем нічого не розбирає заново.

Виміряно на зібраному бінарнику: **~1 % одного ядра в простої** з блимаючим курсором, ~3 % під час швидкого прокручування колесом.

## Субагенти та довгі команди

**Субагенти.** Інструмент `task` запускає другого агента з власним контекстом і тими самими інструментами, а потім повертає лише його звіт — корисно для роботи, яка інакше залила б контекст того, хто викликав. Звіт обрізається на 6 000 символах, бо він потрапляє в контекст викликача, а стенограма показує його поступ одним рядком, який замінюється на кожному кроці, а не рядком на крок. Вкладені субагенти пропонуються, поки лишається глибина, обмежена двома рівнями, щоб рекурсія не розбіглася. Стенограма показує кожен крок, який робить субагент.

**Повільні команди переводяться, а не вбиваються.** Команда на передньому плані, яка все ще виконується після **60 секунд**, переміщується у фоновий режим, і агентові про це повідомляють, замість того щоб блокувати хід:

```
'sleep 75' is still running after 60s, so it was moved to the background as 'bg-1'.
Carry on; you will be told when it finishes, or poll it with {"output_id": "bg-1"}.
```

**Завершення перериває.** Коли фонова команда закінчується, поточний хід переривається, і агент отримує вивід, тож результат ніколи не губиться тихо за довгою роботою:

```
• interrupted: a background command finished
```

## Диктування

Кнопка мікрофона в нижньому куті (`ctrl-r` робить те саме) диктує в промпт: натисніть її, говоріть, натисніть знову. Текст надходить, поки ви говорите, бо розпізнавач працює потоком, а на кнопці йде лічильник, поки вона слухає.

Розпізнавач — це **whistle** — локальний мовленнєвий рушій від Cactus — запущений як `whistle --mic`. Саме цей режим робить його потоковим: він записує сирий моно 16 кГц із `pw-record` від pipewire по секунді, проганяє кожну секунду через потоковий декодер і друкує один рядок JSON на кожне оновлення (`text` — це те, що зафіксовано, `pending` — те, що ще в дорозі). Символ нового рядка на його stdin завершує потік і скидає залишок. Команда, мова, слова-підказки та джерело аудіо беруться із середовища:

Записувач — власний для платформи: `pw-record` (pipewire) на Linux, `ffmpeg` з avfoundation на macOS, `ffmpeg` з dshow на Windows (`WHISTLE_SOURCE` вибирає пристрій введення, `WHISTLE_RECORDER` замінює команду цілком). Сам застосунок лише запускає `EXP1_DICTATE --mic` і читає його рядки JSON, тож підійде будь-який розпізнавач, що працює потоком так само; без нього натискання кнопки мікрофона каже про це в нижньому рядку, і більше нічого не відбувається.

```sh
EXP1_DICTATE=/path/to/whistle     # default: whistle on PATH
EXP1_DICTATE_LANG=en              # default: whatever it detects
EXP1_DICTATE_KEYWORDS=country,Americans
WHISTLE_SOURCE=…                  # default: the system's own input
```

Диктування доступне лише на Linux, бо таким є записувач; решта агента — ні.

Цей режим локальний для цієї копії whistle: логіка лежить у його бібліотеці як тип `Dictation` (`start`, `next`, `finish`), а його `main.rs` — тонкий цикл над нею. У whistle тут немає власного репозиторію, тож у свіжої копії від його автора ці два файли треба застосувати заново, або вказати `EXP1_DICTATE` на щось, що говорить тим самим протоколом. Розпізнавач, який не знає `--mic`, не ігнорується: він каже про це, своїми словами, в нижньому рядку.

## Провайдери

`/login` відкриває панель вибору провайдерів; `/scoped-models` вирішує, які з їхніх моделей пропонує `/model` (порожньо означає всі, а область зберігається в `settings.json`). Панель — простий абетковий список, а курсор відкривається на провайдері, який використовується, тож нічого не треба шукати за позицією. Вибір провайдера, у якого вже виконано вхід, перемикає на нього й каже про це; вибір того, що вже використовується — або запуск `/login <id>` — навмисно виконує вхід заново. Вхід за кодом пристрою відкриває сторінку постачальника в браузері та друкує URL і код як запасний варіант.

**Один ключ може покривати кілька провайдерів.** `opencode-go` і `opencode-zen` — це один акаунт за двома базовими URL, тож вхід у будь-який із них зберігає ключ для обох (`providers::key_group` називає групи). Шлюзи opencode також маршрутизують за сесією: кожен запит несе `x-opencode-session`, `x-opencode-project` і `x-opencode-client`, без яких шлюз відмовляє йому відразу («Request is missing x-opencode-session»).

П'ять протоколів передачі покривають усе, реалізоване тут: API **OpenAI chat-completions**, який використовує десяток постачальників, **OpenAI Responses**, **Anthropic messages**, рідний **Gemini `generateContent`** від Vertex AI і **бекенд Codex**, з яким говорить `openai (auth)`. Усі передають SSE потоком, і всі декодуються в той самий потік подій, який породжує клієнт Codex, тож цикл агента не знає, з яким із них говорить.

Ключі зберігаються окремо для кожного провайдера в `~/.config/exp-1/credentials.json`, з правами `0600`. `openai (auth)` натомість тримає `auth.json` у стилі Codex, `google vertex` використовує те, у чому вже виконано вхід через `gcloud auth application-default login` (а `GOOGLE_CLOUD_PROJECT` і `GOOGLE_CLOUD_LOCATION` називають проєкт і регіон), а провайдери з кодом пристрою кладуть отриманий токен у той самий файл облікових даних.

## Режими

`shift + tab` перемикає сесію між двома режимами, і нижній рядок каже, який активний:

- **build** — усе так, як описано тут.
- **plan** — інструменти, що змінюють файли (`write`, `edit`, `delete`), відхиляються *і* вилучаються зі списку інструментів, тож модель досліджує та пропонує план замість редагування. Очікується, що `shell` лишається лише для читання. Формулювання живе в `prompts/plan.md`, редагованому, як і решта.

## Дозволи

`~/.config/exp-1/permissions.json` — це список винятків; виклик, що не збігається з жодним правилом, виконується. Вирішує перший збіг:

```json
{
  "rules": [
    { "action": "shell", "resource": "rm -rf *", "effect": "deny" },
    { "action": "write", "resource": "/etc/*", "effect": "ask" },
    { "action": "fetch", "resource": "*", "effect": "allow" }
  ]
}
```

`action` — це назва інструмента або `*`, `resource` — те, чого торкається виклик: шлях для файлових інструментів, командний рядок для `shell`, URL або запит для мережевих; `*`/`?` працюють як шаблони. `effect` — це `allow`, `ask` або `deny`. `ask` викликає панель запитань і тримає виклик, доки на нього не дадуть відповідь (дві хвилини, потім виклик відхиляється). Правила застосовуються і до субагентів.

`ctrl + shift + a` перемикає режим дозволів: **always ask** (типовий для чистої установки) змушує `write`, `edit`, `delete` і `shell` піднімати запитання, **never ask** виконує їх без запитання, а **ask only commands** питає лише за `shell`. Інструменти лише для читання не питають ніколи, а правило з `effect: deny` відмовляє в кожному режимі — режим ніколи не пом'якшує заборону.

## Інструкції проєкту

`AGENTS.md` читається з робочого каталогу та кожного батьківського над ним, від найзовнішого, і додається до системного промпту — тож власні правила репозиторію доходять до моделі, не вставляючись у розмову. `/init` записує початковий файл.

## Збої провайдера

Збій на боці сервера або транспорту повторюється один раз через дві секунди; відхилений запит (4xx) — ні. Коли основна модель продовжує збоїти, `fallback_model` у `settings.json` називає модель того самого провайдера, яку пробують один раз, перш ніж від ходу відмовляться, і перемикання позначається у стенограмі.

## Навички

Навичка — це каталог із `SKILL.md` усередині, такої форми, яку використовують Claude Code та opencode. Встановлення навички робить її командою:

```sh
exp-1 install ~/skills/pdf-tools          # a directory with SKILL.md
exp-1 install notes.md                    # a single markdown file
exp-1 install tools.zip                   # an archive (unzip or tar)
exp-1 install https://example.com/skill.md
```

Файли потрапляють у `~/.config/exp-1/skills/<name>/` і називаються за полем `name:` із frontmatter, коли воно є, а інакше — за іменем файлу або каталогу. Встановлені навички з'являються поруч зі вбудованими командами у вікні доповнень і в довідці порожнього стану, а `/<name>` запускає одну з них: сервер читає інструкції навички, записує їх у розмову як завдання і дає моделі їх виконати. `description:` із frontmatter — це те, що показує панель вибору.

## MCP-сервери

Інструменти з [MCP](https://modelcontextprotocol.io)-серверів пропонуються моделі поряд із вбудованими. Список живе в `~/.config/exp-1/mcp.json`, точно в тій формі, яку використовує opencode, тож запис можна переносити між ними:

```json
{
  "mcp": {
    "context7": { "type": "remote", "url": "https://mcp.context7.com/mcp" },
    "blender": {
      "type": "local",
      "command": ["blender-mcp"],
      "environment": { "BLENDER_HOST": "localhost" }
    }
  }
}
```

- Сервери `local` запускаються, і з ними розмовляють через stdio; до `remote` звертаються через HTTP, з відповіддю у вигляді JSON або SSE. `"disabled": true` пропускає сервер, не видаляючи його, а `"headers"` додає те, що потрібно віддаленому серверу.
- Інструменти доходять до моделі як `<server>_<tool>`, обидві половини очищено так само, як це робить opencode (`context7_resolve-library-id`), тож два сервери ніколи не зіштовхнуться.
- Сервери підключаються **у фоні** під час запуску: повільний або мертвий ніколи не затримує агента, і про нього повідомляють, а не відкидають — `/mcp` перелічує кожен сервер із кількістю його інструментів або помилкою, з якою він не впорався.

## Фоновий сервер

Змодельовано на демоні opencode. **Звичайний запуск `exp1-agent` піднімає сервер і приєднується до нього**, точно як типова команда opencode бере `daemon.transport()` і передає його UI.

Наслідок і є суттю: закриття UI лишає сервер працювати, тож наступний запуск використовує теплий процес повторно. Сервер використовується повторно лише коли він **і** тієї самої версії, **і** тієї самої збірки: `server.json` записує розмір і час зміни виконуваного файлу, тож перезібраний після старту сервера клієнт замінює його, а не говорить протоколом, якого сервер уже не розуміє. Виміряно на цій машині:

| | холодний запуск | наступний запуск |
| --- | --- | --- |
| Запуск UI → перший кадр | 189 ms | **84 ms** |
| RSS UI | 14.4 MB | 16.0 MB |
| RSS сервера | 15.2 MB | 20.5 MB (після ходу) |

Виміряно знову з п'ятьма відкритими сесіями одночасно:

| | один сервер + 5 UI | п'ять окремих процесів |
| --- | --- | --- |
| у простої | 97 MB (15 + 5 × 16) | 183 MB (5 × 37) |
| із вбудованим titler | 143 MB | 423 MB (5 × 85) |

Сервер ледачий щодо того, що завантажує: клієнт Codex з'являється на першому ході (+5 MB), а вбудований titler — лише якщо назву справді генерують локально (+48 MB, тому `auto` віддає перевагу моделі). У цій ледачості — більша частина суті: 48 MB ваг сплачуються один раз на всі сесії на машині, а не раз на процес.

Дорогий стан, спільний для всієї машини — реєстр інструментів і ~49 MB моделі titler — живе в одному сервері, а клієнт Codex будується тоді, коли його вперше потребує запит протоколу Codex, тож машина, підключена до будь-якого іншого провайдера, запускає сервер без облікових даних Codex. Кожен UI — тонкий клієнт, тож N паралельних сесій коштують `1 x 63 MB + N x 15 MB` замість `N x 61 MB`, і лише перший запуск платить за холодний старт.

```sh
exp1-agent serve                 # run the server in the foreground
exp1-agent service start         # spawn it detached (survives the launcher)
exp1-agent service status        # pid, url, version, health
exp1-agent service stop          # SIGTERM, then SIGKILL after a grace period
exp1-agent service restart
exp1-agent service password      # print, or set with an argument
```

- **Реєстрація**: `~/.local/state/exp-1/server.json` містить `{id, version, url, pid}`. Клієнт читає його, перевіряє `/health` з таймаутом 2 с і використовує сервер повторно лише тоді, коли збігається і версія — застарілий або чужий сервер спершу зупиняється.
- **Пароль**: `~/.local/state/exp-1/password`, 32 випадкові байти, права `0600`, зберігається між перезапусками, тож щойно запущений клієнт перепідключається без жодних вказівок.
- **Відокремлений запуск**: `exp1-agent serve --register` у власній групі процесів із закритими стандартними потоками, тож він переживає того клієнта, який його запустив.

### HTTP API

Усі маршрути вимагають `Authorization: Bearer <password>`.

| Метод | Шлях | Призначення |
| --- | --- | --- |
| `GET` | `/health` | живучість і версія |
| `GET` | `/sessions` | перелічити живі сесії |
| `POST` | `/sessions` | створити одну; `x-exp1-directory` задає її робочий каталог |
| `GET` | `/sessions/{id}` | повний знімок |
| `POST` | `/sessions/{id}/prompt` | почати хід |
| `GET` | `/sessions/{id}/events` | SSE: знімок, дельти, інструменти, використання, назва, done, idle |
| `POST` | `/sessions/{id}/answer` | відповісти на `ask_question`, що чекає |
| `POST` | `/sessions/{id}/interrupt` | перервати поточний хід |
| `GET` | `/models` | каталог зі справжніми зусиллями кожної моделі. `?all=1` ігнорує область: панель, яка задає область, потребує моделей поза нею |

Сесія несе власний робочий каталог, тож один сервер обслуговує кілька проєктів; каталог надходить разом із `POST /sessions`, а не фіксується під час старту сервера.

## Автоматичне ущільнення

Довга розмова підсумовується, перш ніж вона зможе переповнити вікно контексту. Після кожного ходу сервер порівнює `input_tokens` запиту з `context_window` моделі з каталогу Codex і ущільнює, коли розмова сягає **95 %** від нього:

```
Context at 7378 of 258400 tokens (95% threshold) — compacting
Conversation compacted; continuing from the summary
```

Ущільнення надсилає розмову моделі з промптом для підсумовування та структурованим шаблоном, який використовує opencode — Objective, Important Details, Work State (Completed / Active / Blocked), Next Move, Relevant Files — а виводи інструментів обрізаються до 2000 символів, щоб підсумовувач не потонув.

Переписана розмова — це **підсумок, за яким ідуть останні п'ять ходів користувача, збережених дослівно**, кожен із викликами інструментів агента та їхніми результатами, тож нитка поточної розмови не губиться:

```
[user]      Summary of everything so far: ## Objective …
[user]      Turn two: run shell ["seq","1","900"] and reply OK.
[call]      shell
[result]    exit_code: 0 1 2 3 …
[assistant] OK
… four more turns …
```

Факт, названий до ущільнення, усе ще відомий після нього. Якщо один із цих ходів сам величезний, найстаріші записи хвоста відкидаються, доки результат знову не вміститься у вікно, тож один величезний вивід інструмента не може змусити розмову ущільнюватися знову й знову.

Частка задається `EXP1_COMPACT_PERCENT`, якщо потрібна інша, — це також спосіб перевірити цей шлях, не заповнюючи вікно на 272 000 токенів.

Розмова зберігає до 5 000 повідомлень стенограми на диску; власний контекст моделі обмежується окремо, обрізанням і ущільненням, тож довга сесія лишається читабельною, не коштуючи токенів.

## Збереження

Конфігурація живе в `~/.config/exp-1/` (або `$XDG_CONFIG_HOME/exp-1`); самі розмови — у `~/.cache/exp-1/sessions/` (або `$XDG_CACHE_HOME/exp-1/sessions`), бо стенограма — це кеш: втрата однієї коштує контексту, а не налаштувань. Власні файли демона — `server.json` і `password` — лежать у `~/.local/state/exp-1/`.

| Файл | Містить |
| --- | --- |
| `config/settings.json` | модель, зусилля міркування, тему, режим titler, резервну модель |
| `config/credentials.json` | один API-ключ на провайдера, права `0600` |
| `config/prompts/*.md` | системні промпти, редаговані: `system`, `subagent`, `compaction`, `title`, `plan` |
| `config/permissions.json` | правила allow/ask/deny |
| `config/mcp.json` | MCP-сервери |
| `config/skills/` | встановлені навички, по одному каталогу на кожну |
| `cache/sessions/<id>.json` | одна розмова: назва, обидві стенограми, історія з боку моделі, історія промптів |

Розмова зберігає на диску свої найновіші **250 повідомлень**, а весь кеш підрізається до **250 MB** — найстаріші файли першими — коли стартує сервер. Старіше компонування, де все лежало в `config/exp-1/sessions/`, переноситься під час першого запуску після зміни.

Налаштування записуються під час виходу із застосунку; сесія записується після кожного завершеного ходу, тож збій коштує щонайбільше хід, що виконувався.

Вбудований titler — необов'язкова фіча: `cargo build --release --no-default-features` лишає його поза збіркою й забирає разом із ним усю залежність Candle, і назви сесій тоді походять лише від моделі. CI збирає саме так, бо titler тягне за собою Candle: крейт лежить у дереві, але релізу не доводиться за нього платити.

Промпти — це файли, а не константи: `~/.config/exp-1/prompts/system.md` (власні інструкції агента), `subagent.md`, `compaction.md` і `title.md` записуються під час першого запуску й читаються на кожен запит, тож редагування застосовується до наступного ходу без перезбирання. Порядок визначення моделі та зусиль на старті: **командний рядок → збережені налаштування → перша в каталозі модель**.

**Кожен запуск починається з порожньої сесії.** Нічого не відновлюється автоматично — `/sessions` відкриває панель вибору збережених розмов, найновіші першими, кожна показана зі своєю згенерованою назвою, id і часом останнього використання. Список обмежено каталогом: сесія видима там, де вона почалася, будь-де нижче цього, і всюди, якщо вона почалася в `$HOME` («глобальні»). Сам `$HOME` перелічує лише глобальні, тож він не стає каталогом усіх проєктів. Вибір однієї зберігає розмову, яку ви залишаєте, і завантажує вибрану. `/clear` покидає поточну розмову та починає нову, зберігаючи ваші налаштування.

### Назви сесій

Назви походять від вбудованого **titler** — локальної T5 (7.6M параметрів, 3 шари енкодера та 3 шари декодера), яка працює через Candle у цьому процесі й скомпільована в агент із `src/titler.rs`. Ваги (`Cyronius/titler`) читаються з кешу Hugging Face і завантажуються щонайбільше раз на процес, тож коли вони на диску, генерування назв локальне, миттєве й безкоштовне.

Генерування виконується в блокуючій нитці в момент завершення першого ходу, ніколи в нитці UI. Сесії з батьком — бічний чат — не називаються взагалі, бо належать розмові, за якою йдуть. Використовується багатомовний шлях бібліотеки (а не сирий), тож мову визначають, і неанглійський промпт спершу перекладається англійською. Сесії називають один раз, а попередній перегляд, узятий із промпту, — це те, що показує панель вибору, доки не надійде назва.

**Хто називає сесію — це налаштування**, `titler` у `settings.json`:

| Значення | Поведінка |
| --- | --- |
| `auto` (типово) | спершу модель Codex, вбудований titler як запасний |
| `local` | лише вбудований titler — без витрат на API, слабші назви |
| `remote` | лише модель Codex |

Назви запитують у дешевого рівня `luna` з каталогу, а не в моделі самої сесії — та сама ідея, що й opencode, який просить у провайдера його малу модель — а токени, які коштує назва, додаються до використання сесії, як і будь-який інший виклик.

`/retitle` називає сесію заново, цього разу з початкового запиту плюс недавньої розмови (обмеженої 8,000 символами), — так opencode перегенеровує назву, коли сесію перейменовують на пусто. Сам промпт живе в `prompts/title.md` і є повним документом у стилі opencode: завдання, правила (та сама мова, що й у користувача, ≤50 символів, зберігати точні терміни та числа, ніколи не відповідати на запитання) і десять розібраних прикладів.

`auto` навмисно веде моделлю Codex. Titler на 7.6M чесний щодо свого розміру: з тими самими російськими промптами він видав `Understanding Two Plus Terms` для «сколько будет два плюс два» і `Request for Sign` для запиту таблиці, бо безкоштовний перекладач Google передає «табличку» як «sign», і мала модель потім дає назву перекладеному неправильно. Модель Codex називає ті самі промпти `Сколько будет два плюс два?` і `Формула корней квадратного уравнения в LaTeX`. Саме для цього шляху LLM існує `prompts/title.md` — вбудована модель бере перше повідомлення як є й повністю ігнорує файл.

## Обмеження

Хід виконує щонайбільше 200 раундів інструментів; якщо він колись до цього дійде, стенограма скаже про це, а не спиниться мовчки.

**Економія токенів.** Запити навмисно лишаються малими: `read` ділить на сторінки, `grep` обмежує свої збіги, довгий вивід команди зберігає обидва кінці, звіт субагента обрізається на 6 000 символів, а перед кожним запитом найстаріші виводи інструментів — поза останніми двома ходами — замінюються однорядковою приміткою про те, що було відкинуто. Модель може перезапустити інструмент для всього, що їй ще потрібне, а стенограма, яку бачить користувач, зберігає повний текст.

**Паралельні виклики.** Повідомлення моделі може просити кілька інструментів одразу. Серії викликів лише для читання (`read`, `grep`, `count`, `ast`, `fetch`, `websearch`) виконуються одночасно; усе, що пише, зберігає свій порядок, тож запис, за яким іде читання того самого файлу, не може бути переставлено.

Це MVP. Відомі прогалини:

- Vertex приймає лише облікові дані gcloud за замовчуванням для застосунку; ключ сервісного акаунта, який потребує підписаного JWT, не створюється.
- Бічний чат бачить усю основну розмову на кожне запитання — основна історія читається, ніколи не записується — тож відповідь `/btw` має повний контекст, поки основна гілка лишається недоторканою.
- Немає скасування потоку, крім переривання задачі.
- Команди виконуються без пісочниці.

## Перевірено на

Деталі протоколу звірено з джерельним кодом `openai/codex` і підтверджено живими запитами: ендпойнт і заголовки, ротація refresh-токена, потокове передавання тексту, повний цикл `function_call` і багатоітераційний цикл інструментів, який записав файл.
